# AIFR — AI FOR ROBOTICS
## Multi-Robot Autonomous Cafeteria Food Delivery Simulation

### 1. Project Overview

AIFR is a 3D multi-robot autonomous food delivery simulation developed inside Blender.

The objective is to simulate multiple autonomous mobile robots operating inside a cafeteria, accepting food orders, collecting food from service counters and delivering it to customer tables.

The system will demonstrate:

- Autonomous robot navigation.
- Global route and task optimization.
- Local obstacle avoidance.
- Robot localization and state estimation.
- Multi-robot coordination.
- Order management and scheduling.
- Collision prevention.
- Real-time simulation and visualization.

The project uses a cafeteria environment instead of the originally considered warehouse environment.

**Important:** This is an actual robotics simulation project, not simply a 3D animation.

### Order lifecycle

```text
CREATED
   ↓
PREPARING
   ↓
READY
   ↓
ASSIGNED
   ↓
TO_PICKUP
   ↓
LOADING
   ↓
TO_CUSTOMER
   ↓
UNLOADING
   ↓
DELIVERED
```

Additional terminal states: FAILED and CANCELLED.

### Scheduling policy

A single global FCFS queue is shared by all robots.

- Orders enter the queue when READY.
- READY timestamp determines priority.
- Sequence number breaks timestamp ties.
- Robot IDs determine deterministic assignment order when multiple robots become available simultaneously.
- No distance-based or route-cost-based scheduling.
- Each robot handles one active order.
- After delivery, a robot becomes available immediately without returning to base.

### Fault handling

- Faulty robot becomes FAULTED.
- Its active order becomes FAILED.
- Faulty robots cannot receive new orders.
- Failed orders are not automatically requeued.
- Manual retry creates a new order.
- Cancellation is rejected after LOADING begins.

### Configuration

- Default fleet size: 3.
- Maximum fleet size: 64.
- Simulation tick: 50 ms, configurable.

- 511 tests were independently rerun successfully in the available Python environment.

## Stage 7 — DWA Local Navigation and Dynamic Obstacle Avoidance

**Objective:** Enable robots to navigate safely around nearby obstacles.

### DWA — Dynamic Window Approach

Responsibilities:
- Select feasible linear and angular velocities.
- Evaluate short-horizon trajectories.
- Avoid nearby obstacles.
- Handle dynamic obstacles.
- Follow global route guidance.
- Recover from local navigation difficulties.

DWA is the local motion planner, not the global task scheduler.

The global navigation system supplies route guidance; DWA handles local motion decisions.

**Deliverable:** A robot capable of navigating around dynamic obstacles while progressing toward its destination.

## Stage 8 — ALNS Global Optimization and Multi-Robot Coordination

**Objective:** Optimize routes and coordinate multiple robots.

### ALNS — Adaptive Large Neighborhood Search

Intended responsibilities:
- Global route optimization.
- Multi-robot route optimization.
- Optimization of travel cost and route efficiency.
- Potential task/route optimization, depending on the final formulation.

The precise optimization problem must be defined before implementation.

### Multi-robot coordination

Responsibilities:
- Multiple robots operating simultaneously.
- Conflict detection.
- Narrow corridor management.
- Path reservations or equivalent coordination.
- Safe waiting and yielding.
- Deadlock detection and resolution.
- Collision prevention.

The cafeteria's narrow aisles make this stage especially important.

ALNS should not replace local motion control. DWA remains responsible for local navigation.

**Deliverable:** Multiple robots delivering orders simultaneously with optimized routes and safe coordination.

# 6. NAVIGATION ALGORITHM RESPONSIBILITY

This separation is mandatory.

| Algorithm | Responsibility | Must NOT be used for |
|---|---|---|
| ALNS | Global route/task optimization | Low-level velocity control |
| DWA | Local motion planning and obstacle avoidance | Order scheduling or localization |
| EKF | Localization and state estimation | Route planning or obstacle avoidance |

The algorithms must remain modular and communicate through clearly defined data interfaces.

Their exact integration should be designed when the relevant stages begin.

# 7. DEVELOPMENT PRINCIPLES

The project follows these rules:

1. Preserve completed stages.
2. Never rewrite working code unnecessarily.
3. Implement incrementally.
4. Keep Blender-specific code isolated.
5. Use pure Python for testable core logic.
6. Minimize dependencies.
7. Avoid giant monolithic scripts.
8. Do not implement future-stage features prematurely.
9. Test each stage before proceeding.
10. Validate complete robot footprints, not just robot centre positions.
11. Never fabricate environmental geometry.
12. Keep navigation algorithms within their intended responsibilities.

We prefer a simple, correct, maintainable implementation over unnecessary architectural complexity.
